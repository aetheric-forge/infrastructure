# Secrets Management

Secrets are one of the few areas where platform automation must balance convenience, security, and operational practicality.

Aetheric Forge uses a layered approach to secret management that combines GitOps, encryption, and bootstrap ownership.

The goal is to make secrets manageable without requiring them to be stored in plaintext or manually recreated after every deployment.

---

## Why Secrets Matter

Many platform services require sensitive information.

Examples include:

- API tokens
- DNS credentials
- Repository credentials
- Certificate authority passwords
- Service account credentials
- Database passwords

Unlike most platform configuration, these values cannot safely be committed to Git in plaintext.

---

## Design Principles

The secrets architecture is built around several principles:

- Secrets should never be stored in plaintext within Git
- Secrets should remain recoverable
- Secret ownership should be explicit
- GitOps should manage secret configuration where practical
- Bootstrap should manage secrets required before GitOps can operate
- Secret rotation should be possible without rebuilding the platform

---

## Ownership Model

Not all secrets are managed the same way.

Aetheric Forge separates secrets into ownership categories.

```text
Bootstrap Secrets
        │
        ▼
Enable GitOps

GitOps Secrets
        │
        ▼
Enable Platform Services

Runtime Secrets
        │
        ▼
Generated By Controllers
```

Understanding ownership is essential when troubleshooting or rotating credentials.

---

## Bootstrap Secrets

Bootstrap secrets are required before GitOps can become operational.

Examples include:

- Repository SSH credentials
- AGE private key references
- RFC2136 TSIG credentials
- External DNS provider API tokens

These secrets are supplied during configuration and bootstrap.

Without them, GitOps cannot establish control of the platform.

---

## GitOps-Managed Secrets

Some secrets may be stored in Git after encryption.

Examples include:

- Application credentials
- Service configuration secrets
- Platform integration credentials

These secrets are managed declaratively through GitOps.

The encrypted secret becomes part of the desired platform state.

---

## Runtime Secrets

Some secrets are generated dynamically by platform controllers.

Examples include:

- Issued TLS certificates
- Certificate private keys
- Service account tokens
- Generated application credentials

These resources are created at runtime and should generally not be edited manually.

---

## SOPS

Aetheric Forge uses SOPS to protect secrets stored in Git.

SOPS encrypts secret values while allowing them to remain version controlled.

```text
Plaintext Secret
        │
        ▼
      SOPS
        │
        ▼
Encrypted Secret
        │
        ▼
       Git
```

This allows secrets to participate in GitOps workflows without exposing sensitive information.

---

## AGE

SOPS uses AGE encryption for key management.

AGE provides:

- Modern cryptography
- Simple key management
- Portable key files
- Human-readable public keys

The AGE key pair becomes the trust anchor for encrypted Git-managed secrets.

```text
AGE Public Key
        │
        ▼
Secret Encryption

AGE Private Key
        │
        ▼
Secret Decryption
```

Protecting the AGE private key is critical.

Loss of the private key may make encrypted secrets unrecoverable.

---

## Secret Flow

The typical lifecycle of a GitOps-managed secret is:

```text
Create Secret
      │
      ▼
Encrypt With SOPS
      │
      ▼
Commit To Git
      │
      ▼
Argo CD Reconciliation
      │
      ▼
Kubernetes Secret
```

The plaintext secret exists only during creation and deployment.

The repository contains only the encrypted representation.

---

## Secret Rotation

Credentials occasionally need to be replaced.

Examples include:

- Expired API tokens
- Repository credential changes
- DNS credential rotation
- Security incidents

Rotation should occur through the owning system.

Examples:

| Secret Type              | Rotation Method                           |
| ------------------------ | ----------------------------------------- |
| SOPS-managed secret      | Update, re-encrypt, commit                |
| Bootstrap credential     | Update configuration and bootstrap inputs |
| Runtime-generated secret | Regenerate through the owning controller  |

Ownership determines the correct rotation process.

---

## Relationship to GitOps

GitOps manages secret declarations.

GitOps does not manage plaintext secrets.

```text
Git
 │
 ▼
Encrypted Secret
 │
 ▼
Argo CD
 │
 ▼
Kubernetes Secret
```

This allows sensitive data to participate in reconciliation without exposing the underlying values.

---

## Relationship to Bootstrap

Bootstrap is responsible for establishing access to secret management.

Examples include:

- Repository credentials
- AGE key references
- DNS credentials
- External provider credentials

Once bootstrap completes, GitOps can begin managing encrypted platform secrets.

```text
Bootstrap
     │
     ▼
Secret Access
     │
     ▼
GitOps
     │
     ▼
Platform Secrets
```

Bootstrap creates trust.

GitOps manages configuration.

---

## Failure Recovery

Secret recovery depends on ownership.

To recover encrypted Git-managed secrets, the following must be preserved:

- Git repository
- AGE private key
- Bootstrap configuration

These components together allow the platform to reconstruct secret state during recovery operations.

For this reason, AGE private keys should be backed up securely.

---

## Design Goals

The secrets architecture is designed to provide:

- Secure secret storage
- GitOps compatibility
- Recoverable deployments
- Clear ownership boundaries
- Encrypted version control
- Minimal manual handling

The ultimate goal is simple:

> Secrets should participate in automation without becoming part of the public record.

---

## Summary

Secrets occupy a unique position within the platform.

Unlike most configuration, secrets require both automation and protection.

Aetheric Forge achieves this through:

- Bootstrap ownership
- SOPS encryption
- AGE key management
- GitOps reconciliation
- Runtime controller ownership

```text
Bootstrap
     ↓
Trust

SOPS + AGE
     ↓
Protection

GitOps
     ↓
Distribution

Kubernetes
     ↓
Consumption
```

Together these components provide secure and reproducible secret management throughout the platform lifecycle.

## Secrets in Practice

Most application secrets are stored as encrypted Kubernetes Secret manifests.

A typical workflow is:

```text
Create Secret Manifest
         │
         ▼
Encrypt With SOPS
         │
         ▼
Commit To Git
         │
         ▼
Argo CD Reconciliation
         │
         ▼
Kubernetes Secret
```

For example, an application may require a database password:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: application-secret
type: Opaque
stringData:
  database-password: change-me
```

This manifest would be encrypted using SOPS and stored in Git as:

```text
secrets.enc.yaml
```

The encrypted file can be safely committed to the repository.

During reconciliation, the secret is decrypted and applied to the cluster.

From the perspective of GitOps, encrypted secrets behave like any other managed resource.

The primary difference is that the repository stores the encrypted representation rather than the plaintext value.

## Giving a Service Its Own SeaweedFS Credentials

Each service that writes to SeaweedFS gets its own S3 identity, limited to one bucket, so a leaked key exposes one bucket and not the others.

`create_seaweedfs_client_secret` in `scripts/bootstrap-secrets.sh` does this in one step:

```bash
create_seaweedfs_client_secret IDENTITY BUCKET NAMESPACE SECRET_NAME OUT_FILE
```

It writes a SOPS-encrypted Secret (`access-key-id`, `secret-access-key`) to `OUT_FILE` for the service to mount, and adds the same pair as an identity in `seaweedfs-s3-config`. It is add-only: the identities already there, and the keys Velero and CNPG hold, are never regenerated. Rerunning does nothing, and a run that stopped between the two writes is finished on the next run.

To use a new bucket:

1. Add the bucket to `createBuckets` in `platform/services/seaweedfs/base/kustomization.yaml`.
2. Call `create_seaweedfs_client_secret` from `create_gitops_artifacts`, and add `OUT_FILE` to the service's `ksops-secrets.yaml`.
3. Commit the changed `seaweedfs-s3-config.enc.yaml` and the new secret file.
4. `make create platform`. The bucket Job removes itself ten minutes after it finishes. If the previous one is still there, delete it first (`kubectl -n seaweedfs delete job seaweedfs-bucket-hook`), because a Job's template can't be changed in place.
5. Restart SeaweedFS so it loads the new identity: `kubectl -n seaweedfs rollout restart deploy/seaweedfs-all-in-one`.

`scripts/tests/test_seaweedfs_identities.py` checks this offline with a throwaway key.
